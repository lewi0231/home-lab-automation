I'm running Proxmox on a Dell Optiplex 7050 Micro (16GB RAM, 512GB SSD)—a classic homelab box. Like many, I dove into Kubernetes out of curiosity and a love for tinkering. But in the process, I tried setups that just don't fit the realities of a modest homelab.

One of those experiments was Longhorn. I gave it a shot, thinking distributed storage would be cool. But Longhorn only shines if you dedicate at least three nodes with decent resources. My setup? Seven VMs, all sharing just 16GB of RAM. You can probably guess where this is going.

## The Setup That Seemed Right

I started with what looked like a solid plan:

- 3 dedicated storage nodes (minotaur, cerberus, griffin)
- Longhorn configured for 3-replica volumes
- Proper node labels and taints

The theory was sound: distributed storage with redundancy. In practice? My Optiplex 7050 was gasping for air.

## The Reality Check

Within days, I started seeing issues:

```# bash
kubectl get nodes
# Nodes showing NotReady
# Pods stuck in ContainerCreating
# Resource pressure warnings
```

The problems were cascading:

1. **Resource Pressure**: Longhorn components competing for limited RAM

   - **How we saw it**: Nodes frequently went <InlineCode>NotReady</InlineCode>, and _kubectl describe node \<node\>_ showed _MemoryPressure_ and _KubeletHasInsufficientMemory_.
   - **What to check**: Use _kubectl top nodes_ to see memory and CPU usage. Look for high usage or nodes with little free memory.

2. **Volume Replica Mismatch**: All volumes created with 3 replicas, but nodes kept failing

   - **How we saw it**: <InlineCode>kubectl get volumes -n longhorn-system</InlineCode> showed volumes in <InlineCode>faulted</InlineCode>, <InlineCode>detached</InlineCode>, or <InlineCode>degraded</InlineCode> states. The <InlineCode>AGE</InlineCode> and <InlineCode>STATE</InlineCode> columns didn't match expectations, and volumes couldn't attach.
   - _What to check_: Inspect Longhorn UI or use <InlineCode>kubectl describe volume \<volume-name\> -n longhorn-system</InlineCode> for error messages about missing replicas or failed scheduling.

3. **Pod Scheduling Conflicts**: Stuck PVCs preventing new pods from starting
   - _How we saw it_: Pods stuck in <InlineCode>ContainerCreating</InlineCode> or <InlineCode>Pending</InlineCode> state. <InlineCode>kubectl describe pod \<pod-name\></InlineCode> revealed events like <InlineCode>FailedAttachVolume</InlineCode> or PVCs stuck in <InlineCode>Terminating</InlineCode>.
   - _What to check_: Use <InlineCode>kubectl get pvc -A</InlineCode> to find PVCs in <InlineCode>Pending</InlineCode> or <InlineCode>Terminating</InlineCode>. Check pod events for volume attachment errors.

If you run into similar issues, start by checking node status (<InlineCode>kubectl get nodes</InlineCode>), resource usage (<InlineCode>kubectl top nodes</InlineCode>), and the state of your volumes and PVCs. The combination of these commands will usually point you to the root cause.

## The Breaking Point

After realising that 3 replicas were not really an option for my limited homelab, I knew that I had too many nodes running and that the recommended 3 node longhorn setup wasn't going to be an option. So, I reduced my cluster from 7 to 4 nodes (1 master, 1 storage, 2 workers). Suddenly, all my volumes were in a "faulted" state:

```# bash
kubectl get volumes -n longhorn-system
NAME                                       STATE       ROBUSTNESS   SCHEDULED   SIZE          NODE       AGE
pvc-5b997bb9-904d-4f4f-b5bd-98bb5cc41b9e   detached    unknown                  10737418240              24h
pvc-6e32ef50-83df-4152-ac68-de1dbad21dd0   attached    degraded                 2147483648    minotaur   24h
pvc-d071263c-6cd1-45bf-b7e3-d6681dd35a6c   detaching   faulted                  8589934592               24h
```

Every volume was created with 3 replicas, but I only had 1 storage node. Longhorn couldn't maintain the required replication, so volumes became faulted and unusable.

## The Solution: Local-Path Provisioner

K3s comes with a built-in storage solution that I'd been ignoring: <InlineCode>local-path</InlineCode> provisioner. It's simple, lightweight, and perfect for homelab use. I learn best through trial and error, but in hindsight I would have gone straight to the local-path setup.

One of the big realizations after switching to local-path was that I no longer needed a dedicated storage node. Since local-path just uses the disk of whatever node the pod lands on, it made sense to convert my "storage" node into a regular worker node. This let me make better use of my limited resources, as any node could now run workloads and provide storage for its own pods.

### What Local-Path Does:

- Uses local disk space on each node
- No complex replication logic (unlike Longhorn, which tries to keep multiple copies—"replicas"—of your data across different nodes for redundancy; local-path just writes your data to the node where the pod is running, with no built-in failover or data duplication)
- Minimal resource overhead
- Built into K3s (no additional installation)

### The Migration Process:

1. **Uninstall Longhorn** (this was... interesting):

```# bash
# Set deletion confirmation flag
kubectl -n longhorn-system patch settings.longhorn.io deleting-confirmation-flag --type='merge' -p='{"value":"true"}'
```

This command is required because Longhorn won't let you uninstall it unless you explicitly confirm you want to delete all your data and resources. Setting this flag to <InlineCode>true</InlineCode> tells Longhorn "yes, I really want to remove everything, even if it means losing data."

```# bash
# Uninstall (this failed, so we force deleted)
kubectl delete namespace longhorn-system --force --grace-period=0

# Clean up CRDs

kubectl delete crd backingimagedatasources.longhorn.io backingimagemanagers.longhorn.io # ... (all Longhorn CRDs)`

```

2. **Update Application Configurations**:

```# yaml
# Loki configuration
singleBinary:
  persistence:
    storageClass: local-path # Changed from "longhorn"

# Pi-hole configuration

persistence:
storageClass: 'local-path' # Changed from "longhorn"
```

3. **Fix Prometheus** (it was deployed as a Deployment instead of StatefulSet):

```# yaml
server:
persistentVolume:
  enabled: false # For now, using ephemeral storage
```

### Resource Usage Comparison:

- **Before**: Nodes frequently NotReady, high memory pressure
- **After**: Stable nodes, predictable resource usage
- **Storage**: Simple, reliable, no complex replication overhead

## The Lessons Learned

### 1. Match Tools to Hardware

Longhorn is designed for enterprise clusters with dedicated storage nodes and abundant resources. My 16GB Optiplex was never going to handle it well. With local-path, I could treat all my nodes as workers, making the most of my hardware.

### 2. Simplicity Wins

More moving parts = more things that can break. Local-path has fewer dependencies and is easier to troubleshoot.

### 3. Start Simple, Scale Up

I should have started with local-path and only moved to distributed storage if I actually needed it.

### 4. Resource Reality Check

Always consider your actual hardware constraints before implementing enterprise solutions.

## When to Use Each Solution

### Use Local-Path When:

- ✅ Homelab with limited resources
- ✅ Single-node storage is acceptable
- ✅ You want simplicity and reliability
- ✅ You're learning Kubernetes

### Use Longhorn When:

- ✅ You have dedicated storage nodes
- ✅ You need data redundancy across nodes
- ✅ You have enterprise-level resources
- ✅ You're running production workloads

## The Bottom Line

For my homelab, local-path is the perfect solution. It's:

- **Simple**: Built into K3s, no additional components
- **Reliable**: Fewer moving parts, less to go wrong
- **Efficient**: Minimal resource overhead
- **Maintainable**: Easy to understand and troubleshoot

Sometimes the best solution isn't the most feature-rich one—it's the one that actually works for your specific situation. My cluster is now stable, my monitoring stack runs smoothly, and I'm not constantly fighting resource pressure.

If you're setting up a homelab Kubernetes cluster, start with local-path. You can always upgrade to distributed storage later if you actually need it. But chances are, you won't.

> **Note:** As a result of this migration, I ran into some tricky issues with deleting PersistentVolumeClaims (PVCs). For example, Loki was trying to use a volume that had become detached and stuck in a "Terminating" state. I had to manually remove finalizers from the PVCs and force-delete pods that were referencing missing or faulted volumes. This is a common pain point when removing a storage backend like Longhorn—Kubernetes resources can get stuck if the underlying storage is no longer available.
