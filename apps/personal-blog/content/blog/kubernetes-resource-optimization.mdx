# Homelab Resource Optimization: Making the Most of Limited Hardware

<span style={{ color: '#888', fontSize: '1rem' }}>26 June 2024</span>

Running Kubernetes on limited hardware is like trying to fit a full orchestra into a small room. My homelab runs on a single Optiplex 7050 Micro with 16GB RAM, hosting 7 K3s nodes via Proxmox. My initial setup included Longhorn distributed storage, which I quickly learned was not feasible for my hardware. (You can read more about my Longhorn difficulties in the [ditching-longhorn-for-local-path](./ditching-longhorn-for-local-path) article.)

But that experiment was valuable: it made me painfully aware of just how important resource optimization is in a homelab environment. This article is about the optimization journey that turned my struggling cluster into a stable, efficient system.

## The Reality Check

My initial setup looked reasonable on paper:

- **Hardware**: Optiplex 7050 Micro (16GB RAM, 512GB SSD)
- **Nodes**: 7 K3s nodes (1 master, 3 storage, 3 workers)
- **Monitoring**: Prometheus, Loki, Grafana, Alertmanager
- **Storage**: Longhorn distributed storage

The reality was different:

## The Resource Pressure Problem

### What Was Happening

1. **Memory Pressure**: 16GB total RAM ÷ 7 nodes = ~2.3GB per node
2. **CPU Contention**: Limited CPU cores were shared across many components (Kubernetes control plane, Longhorn, monitoring stack, and application workloads). This meant that when several pods or system processes needed CPU at the same time, they had to wait, causing slowdowns and sometimes pod evictions.
3. **Storage I/O**: Multiple storage systems (Longhorn, local-path, and the underlying VM disks) were all competing for access to the same physical SSD. This led to disk contention, where read/write operations slowed down because too many processes were trying to use the disk at once.
4. **Network Overhead**: Distributed storage like Longhorn requires constant network communication between nodes to replicate data and maintain consistency. On a homelab network, this can create bottlenecks, especially if your nodes are all VMs on the same physical host or if your network hardware is basic.

## The Optimization Strategy

### Step 1: Reduce Cluster Size

I decided to reduce from 7 to 4 nodes:

- **1 master** (chimera)
- **3 workers** (minotaur, griffin, faun)

Since I switched to local-path storage, there was no need for a dedicated storage node—any node could now run workloads and provide storage for its own pods.

### Step 2: Optimize Flux Controllers

Flux was consuming too many resources. I reduced its limits by adding YAML patches directly to my kustomization files, like this:

```yaml
# flux-system/kustomization.yaml
patches:
  - patch: |-
      apiVersion: apps/v1
      kind: Deployment
      metadata:
        name: kustomize-controller
      spec:
        template:
          spec:
            containers:
            - name: manager
              resources:
                limits:
                  cpu: 200m
                  memory: 256Mi
                requests:
                  cpu: 100m
                  memory: 128Mi
    target:
      kind: Deployment
      name: kustomize-controller
```

### Step 3: Optimize Prometheus

The default Prometheus configuration was too aggressive for my hardware. Since Prometheus (and many other services) are managed by Helm, I used a <InlineCode>values.yaml</InlineCode> file to set resource limits and other configuration options:

```yaml
# prometheus/values.yaml
server:
  # Reduce resource limits
  resources:
    limits:
      cpu: 500m # 50% of one CPU core max
      memory: 512Mi # ~537 MB max
    requests:
      cpu: 200m # 20% of one CPU core minimum
      memory: 256Mi # ~268 MB minimum

  # Reduce retention to save storage space
  retention: '7d' # 7 days instead of 15 days
  retentionSize: '2GB' # Limit storage size to 2GB

  # Reduce scrape intervals to lower resource usage
  global:
    scrape_interval: 2m # Scrape every 2 minutes instead of 1 minute
    scrape_timeout: 10s
    evaluation_interval: 2m # Evaluate rules every 2 minutes instead of 1 minute
```

> **Note:** Many of my services are managed by Helm, which is why I use values files for configuration. This makes it easy to version, update, and roll back changes.

### Step 4: Optimize Alertmanager

## Key Optimization Principles

### 1. Start with Resource Limits

Always set resource limits, even if you're not sure what the right values are. A good rule of thumb for homelab setups is to start conservatively:

- **CPU**: Start with 100-500m (0.1-0.5 cores) per pod, depending on the workload
- **Memory**: Start with 128Mi-512Mi per pod
- **Requests**: Set requests to the minimum you think the pod needs to start and run reliably
- **Limits**: Set limits to the maximum you're willing to allow for that pod

Monitor usage and adjust as needed. It's easier to increase limits than to recover from resource exhaustion.

### 2. Monitor and Adjust

Use these commands to monitor resource usage:

```bash
# Check node resource usage
kubectl top nodes

# Check pod resource usage
kubectl top pods --all-namespaces

# Check node conditions
kubectl describe nodes | grep -A 10 "Conditions"
```

### 3. Reduce Polling Intervals

For monitoring systems, longer intervals mean less resource usage:

```yaml
# Instead of 1-minute scraping
scrape_interval: 1m

# Use 2-5 minute intervals
scrape_interval: 2m
```

### 4. Limit Data Retention

Storage is often the bottleneck:

```yaml
# Instead of 15-day retention
retention: "15d"

# Use 7-day retention for homelab
retention: "7d"
retentionSize: "2GB"
```

## Monitoring Your Optimizations

### Set Up Resource Monitoring

```bash
# Create a simple resource monitoring dashboard
kubectl apply -f - <<EOF
apiVersion: v1
kind: ConfigMap
metadata:
  name: resource-monitoring
  namespace: monitoring
data:
  resource-alerts.yaml: |
    groups:
    - name: resource-alerts
      rules:
      - alert: HighMemoryUsage
        expr: (node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes) / node_memory_MemTotal_bytes > 0.8
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "High memory usage on {{ $labels.instance }}"
EOF
```

### Key Metrics to Watch

1. **Memory Usage**: Keep under 80% per node
2. **CPU Usage**: Keep under 70% per node
3. **Disk Usage**: Keep under 85% per node
4. **Pod Restart Rate**: Should be minimal

## Lessons Learned

### 1. Enterprise Defaults Don't Work for Homelab

Most Kubernetes applications are configured for enterprise environments with abundant resources. Homelab environments need different defaults.

### 2. Resource Limits Are Essential

Without resource limits, applications can consume all available resources, causing system instability.

### 3. Monitoring Overhead Matters

Monitoring systems can consume significant resources. Optimize them first.

### 4. Start Conservative, Scale Up

It's easier to increase resource limits than to recover from resource exhaustion.

### 5. Regular Monitoring Is Key

Set up alerts for resource usage and respond before problems occur.

## The Bottom Line

Resource optimization in Kubernetes isn't about squeezing every last drop of performance. It's about creating a stable, predictable environment that works within your hardware constraints.

My 16GB Optiplex now runs a stable 4-node K3s cluster with monitoring, and I have room for applications. The key was understanding that "good enough" is often better than "optimal" in resource-constrained environments.

Start with conservative resource limits, monitor your system, and adjust based on actual usage patterns. Your homelab will thank you.
