## The Fundamental Concepts

### What's a Volume vs PVC?

This was my first confusion. They're not the same thing:

**Volume (PV - Persistent Volume):**

```yaml
# Think of this as the actual storage device
apiVersion: v1
kind: PersistentVolume
metadata:
  name: my-storage
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteOnce
  storageClassName: local-path
  hostPath:
    path: /var/lib/rancher/k3s/storage/pvc-abc123
```

**PVC (Persistent Volume Claim):**

```yaml
# Think of this as a request for storage
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-app-storage
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
  storageClassName: local-path
```

### The Storage Class Connection

Storage classes define how volumes are provisioned:

```bash
kubectl get storageclass
NAME                   PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
local-path (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false                 2d12h
```

When you create a PVC, Kubernetes uses the storage class to:

1. Find or create a matching PV
2. Bind the PVC to the PV
3. Make the storage available to your pod

> **Where do PVCs come from?**
>
> - **Manual creation:** You can create a PVC yourself by writing a YAML manifest and applying it with <InlineCode>kubectl apply -f my-pvc.yaml</InlineCode>. This is common for simple apps, testing, or when you want full control over the storage claim.
> - **Resource-managed creation:** More often, PVCs are created automatically by resources like Helm charts, StatefulSets, or Deployments. For example, when you install Prometheus or Loki via Helm, the chart will usually define a PVC in its templates, and Kubernetes will create it for you. This is the most common pattern for production workloads, as it keeps storage configuration tied to the app.
> - **Why choose one or the other?** If you want to share a volume between multiple pods or manage storage independently of your app, you might create a PVC manually. If you want storage to be managed as part of your app's lifecycle, let the resource (Helm, StatefulSet, etc.) handle it.

## The StatefulSet vs Deployment Confusion

This is where my Prometheus problem got interesting. I discovered that my Prometheus was deployed as a **Deployment** but trying to use persistent storage:

```bash
kubectl get deployment my-prometheus-server -n monitoring -o yaml | grep -A 10 "volumes:"
      volumes:
      - configMap:
          defaultMode: 420
          name: my-prometheus-server
        name: config-volume
      - name: storage-volume
        persistentVolumeClaim:
          claimName: my-prometheus-server
```

### Why This Was Problematic

**Deployments are designed for:**

- Stateless applications
- Interchangeable pods
- No persistent identity

**StatefulSets are designed for:**

- Stateful applications (databases, monitoring systems)
- Stable, unique pod identities
- Individual persistent storage per pod

> **Do you always need a StatefulSet for persistence?**
>
> Not always! You can use a Deployment with a PVC if you only need one pod (e.g., a single-instance app) or if all pods can safely share the same storage. However, if you need each pod to have its own persistent storage (like with databases or Prometheus in HA mode), or you need stable pod identities, you should use a StatefulSet. StatefulSets are the "Kubernetes way" to manage stateful workloads with persistence, but for simple cases, a Deployment with a single PVC can work too. The key is to match the workload's needs to the right controller.

### The Mismatch

My Prometheus was a Deployment trying to use a PVC, but:

1. Deployments expect pods to be replaceable
2. PVCs expect pods to have stable identity
3. Result: Pod couldn't claim the PVC properly

## The Real-World Fix

### Option 1: Disable Persistent Storage (Quick Fix)

I temporarily disabled persistent storage for Prometheus:

```yaml
# prometheus/values.yaml
server:
  persistentVolume:
    enabled: false # Use ephemeral storage instead
```

This worked immediately:

```bash
kubectl get pods -n monitoring | grep prometheus-server
my-prometheus-server-7d89679c87-dvskt   2/2     Running   0   88s
```

### Option 2: Convert to StatefulSet (Proper Fix)

For production, Prometheus should be a StatefulSet:

```yaml
# prometheus/values.yaml
server:
  persistentVolume:
    enabled: true
    size: 8Gi
    storageClass: 'local-path'
```

## When to Use Each Approach

### Use Deployments When:

- ✅ Application is stateless
- ✅ Pods are interchangeable
- ✅ No persistent data needed
- ✅ Examples: Web servers, APIs, frontend apps

### Use StatefulSets When:

- ✅ Application needs persistent data
- ✅ Pods need stable identity
- ✅ Each pod needs its own storage
- ✅ Examples: Databases, monitoring systems, message queues

## The PVC Lifecycle

Understanding this helped me debug many issues:

### 1. Creation

```bash
# PVC is created
kubectl apply -f pvc.yaml

# Kubernetes finds/creates matching PV
kubectl get pvc

my-app-storage    Bound    pvc-abc123-def456-ghi789                  10Gi       RWO            local-path     1m
```

### 2. Binding

```bash
# PVC gets bound to PV

pvc-abc123-def456-ghi789                  10Gi       RWO            Delete           Bound    default/my-app-storage   local-path             1m
```

### 3. Pod Attachment


## Common Storage Problems and Solutions

### Problem 1: PVC Stuck in Pending

```bash
kubectl get pvc
NAME              STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   AGE
my-app-storage    Pending                                    local-path     5m
```

**Solution:** Check if storage class exists and has provisioner:

```bash
kubectl get storageclass
kubectl describe storageclass local-path
```

### Problem 2: Pod Can't Attach Volume

```bash
kubectl describe pod my-pod | grep -A 5 -B 5 "FailedAttachVolume"
```

**Solution:** Check if PVC exists and is bound:

```bash
kubectl get pvc
kubectl describe pvc my-pvc
```

### Problem 3: PVC Stuck in Terminating

```bash
kubectl get pvc
NAME              STATUS        VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   AGE
my-app-storage    Terminating   pvc-abc  10Gi       RWO            longhorn       1h
```

**Solution:** Remove finalizers (nuclear option):

```bash
kubectl patch pvc my-app-storage -p '{"metadata":{"finalizers":null}}' --type=merge
```

## Questions That Deepened My Understanding

As I worked through these issues, I kept asking myself:

1. **Why does Prometheus need persistent storage?**

   - It's a time-series database
   - Historical data is valuable
   - Without persistence, you lose metrics on pod restart

2. **What's the difference between <InlineCode>ReadWriteOnce</InlineCode> and <InlineCode>ReadWriteMany</InlineCode>?**

   - <InlineCode>ReadWriteOnce</InlineCode>: One pod can write, multiple can
     read
   - <InlineCode>ReadWriteMany</InlineCode>: Multiple pods can read and write
   - Most storage classes only support <InlineCode>ReadWriteOnce</InlineCode>

3. **When should I use <InlineCode>emptyDir</InlineCode> vs PVC?**

   - <InlineCode>emptyDir</InlineCode>: Temporary storage, lost on pod restart
   - PVC: Persistent storage, survives pod restarts
   - Use <InlineCode>emptyDir</InlineCode> for cache, temp files
   - Use PVC for important data

4. **What happens if my storage node goes down?**

   - With <InlineCode>local-path</InlineCode>: Data on that node is lost
   - With distributed storage: Data might be available on other nodes
   - Always have backups!

5. **How do I know which storage class to use?**
   - Check what's available: <InlineCode>kubectl get storageclass</InlineCode>
   - Consider your use case (performance, redundancy, cost)
   - Start simple, optimize later

## The Bottom Line

Kubernetes storage isn't just about "where do I put my data?" It's about understanding:

- **What type of application** you're running
- **What type of storage** it needs
- **How to match** the right storage solution to your use case

My Prometheus issue taught me that the storage architecture needs to match the application architecture. A time-series database needs persistent storage, and that means using the right workload type (StatefulSet) with the right storage configuration.

The key is starting simple and understanding the fundamentals before adding complexity. Your storage solution should serve your application, not the other way around.
